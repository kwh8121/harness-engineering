# harness-architect 사용법 — 전체 흐름

설치가 끝난 뒤 실제로 이 스킬을 매일 어떻게 쓰는지 설명한다. 처음 설치한다면
`MIGRATION.md` 를 먼저 본다. 판정을 반증하는 세부 체크리스트는 `CHECKLIST.md`,
Linear 연동 규칙은 `.claude/skills/harness-architect/references/linear-tracking.md` 를 본다.

## 30초 요약

```
개발 업무를 자연어로 말한다
  → 스킬이 6축으로 프로파일링해 H0~H3 중 가장 단순한 레벨을 고른다
  → HarnessSpec(실행 계약)을 계산해 기계로 검증하고 한 화면 요약을 보여준다
  → 승인하면 그 레벨이 정한 절차대로 실행하고, 필요하면 Linear 에 진행을 남긴다
  → 게이트를 전부 통과하고 검증 증거와 함께 완료를 선언한다
```

세 문장으로 줄이면: **묻는다 → 승인한다 → 지켜본다.** 사람이 매 단계 지시할 필요가 없고,
사람이 결정해야 하는 지점(레벨 승인, Human Gate)에서만 멈춘다.

## 트리거하는 방법

특별한 명령어가 없다. 개발 업무를 평소처럼 말하면 된다.

```
"사용자 프로필 페이지에 이미지 업로드 기능을 추가해줘"
"인증 시스템을 JWT 에서 OAuth 로 전환하고 세션도 마이그레이션해줘"
"저장 버튼 색상을 브랜드 파란색으로 바꿔줘"
```

`SKILL.md` 의 트리거 키워드("구현해줘", "기능 추가", "리팩터링", "마이그레이션",
"이 작업 어떻게 진행", "하네스", "에이전트 구조")에 걸리면 자동으로 로드된다.
코드 변경이 없는 질문·조사·설명에는 쓰지 않는다 — 하네스는 실행 계약이지 대화 도구가 아니다.

## Phase 별로 무엇을 보게 되는가

### Phase 0 — 몇 가지만 되묻는다

작업 목표만 말해도 된다. 나머지(범위·제약·수용 기준·위험·환경)는 레포를 읽어서 채운다.
**답에 따라 레벨 판정이나 Human Gate 여부가 바뀌는 것만** 되묻는다 — 예를 들어 "이걸
프로덕션에 반영하나요?" 같은 질문. "어떤 파일을 고칠까요?" 같은 건 묻지 않는다.

목표 자체가 불명확하면(수용 기준을 쓸 수 없는 수준) 브레인스토밍으로 먼저 넘어간다.

### Phase 1~2 — 조용히 판정한다 (사람이 볼 것 없음)

이 두 Phase 는 대화에 드러나지 않는다. 내부적으로 검증 명령을 찾고(`detect-stack.sh`),
6축(scope/coupling/parallelism/uncertainty/risk/side_effect)을 판정해 레벨을 정한다.

### Phase 3 — 여기서 승인을 요청받는다 ★

한 화면 요약을 받는다. 이런 형태다.

```
레벨: H1 (pipeline)
근거: FE 폼·업로드 API·스토리지 연동이 하나의 흐름으로 묶여 있어 구현자 한 명이
      통째로 들고 가야 한다 (H0 은 변경 영역이 3개라 불가)
에이전트: implementer(sonnet), reviewer(opus)
게이트: fast(lint,typecheck) → feature(test) → final(build)
리뷰 루프 상한: 2
Human Gate: 불필요 (로컬 환경, 되돌릴 수 있는 변경)
추적: KOR-9 (Linear, tracking.provider: linear 인 경우)
```

**여기서 반드시 확인할 것**은 `CHECKLIST.md` A-1 의 "거부해야 하는 판정 조합" 표다.
특히 이 세 가지를 스스로 물어본다.

- 한 단계 아래 레벨이 왜 안 되는지 근거가 있는가? (없으면 그 아래가 맞다)
- 영역 개수만으로 병렬 워커를 늘리려 하지 않았는가?
- `risk: high` 를 레벨 승격 근거로 쓰지 않았는가? (risk 는 reviewer·루프 상한만 바꾼다)

승인하면 다음 Phase 로 진행한다. 이상하면 "레벨을 다시 판정해줘" 라고 말하면 된다 —
스킬이 스스로 승인 없이 진행하지 않는다.

### Phase 4 — 레벨에 따라 실행 절차가 다르다

| 레벨 | 무엇이 일어나는가 | 사람이 볼 것 |
|---|---|---|
| **H0** | 직접 구현, 서브에이전트 0개 | 게이트 결과만 (fast→feature→final) |
| **H1** | implementer → 게이트 → reviewer, 루프 ≤2 | 게이트 결과, 리뷰 발견(BLOCKER/MAJOR 만 막힘) |
| **H2** | 조사 2인 병렬 → 계획 → 워커 순차 → integrator | 위 + 조사 보고서 요약, 병합 결과 |
| **H3** | H2 + orchestrator 가 DAG·재라우팅 관리 | 위 + DAG 상태, 실패 시 어디로 되돌아갔는지 |

**H0 은 추적하지 않는다.** 단일 파일 변경까지 Linear 이슈로 만들면 백로그가 오탈자 수정으로
찬다. H1 이상만 `tracking.provider: linear` 일 때 Issue/Project 가 생긴다.

리뷰에서 MINOR·NIT 는 진행을 막지 않는다. BLOCKER·MAJOR 만 막고, 2회(위험도가 높으면 3회)
넘게 반복되면 스킬이 스스로 고치기를 멈추고 남은 발견을 정리해 사람에게 넘긴다 —
이때 "계속 고쳐봐" 라고 재촉하지 말고, 남은 발견을 직접 판단하는 게 맞다
(무한 루프를 막기 위한 의도된 설계다).

### Phase 5 — 완료 선언과 Human Gate

증거 없이 "완료됐습니다" 라고 말하지 않는다. 항상 실행한 검증 명령과 실제 출력이
함께 온다. `human_gate.required` 인 경우(프로덕션 반영, 되돌릴 수 없는 변경, 시크릿·삭제
접촉) 여기서 다시 멈추고 게이트 로그 경로·diff 통계·롤백 절차를 보여준다 — 승인해야
다음으로 간다.

`tracking.human_gate_approval` 이 `linear` 나 `both` 로 설정된 경우, Linear 에서
이슈 상태를 `Todo` 로 바꾸는 것으로도 승인할 수 있다. 대기에는 상한이 있다 — 무한정
기다리지 않고, 상한에 닿으면 알린다.

## Linear 를 함께 쓸 때 보게 되는 것

`tracking.provider: linear` 로 승인하면, 대화창을 안 봐도 Linear 만으로 이 정보를 얻는다.

| 궁금한 것 | Linear 에서 보는 곳 |
|---|---|
| 지금 어디까지 왔나 | 이슈/프로젝트 상태 (Triage→Todo→In Progress→In Review→Done) |
| 무엇이 막고 있나 | `blockedBy` 그래프 (H3 의 DAG 의존이 여기 그대로 표현된다) |
| **왜 통과라고 하는가** | 게이트 코멘트 — 실행한 명령과 exit code, 로그 경로 (전문은 안 붙는다) |
| 무엇이 남았나 | 리뷰 코멘트의 미해결 발견, 초과분은 sub-issue 로 승격 |
| 내가 뭘 승인해야 하나 | `In Review` 상태 + Human Gate 증거 코멘트 |

실제로 이렇게 보이는지 미리 확인하고 싶다면 `LINEAR-DRY-RUN.md` 로 가상 이슈를 만들어
전체 경로를 리허설할 수 있다 (끝나면 정리한다).

## 자주 하는 조작

**레벨이 마음에 안 들 때** — "이건 H2 로 해야 할 것 같은데" 라고 말한다. 스킬은
`references/routing.md` 의 판정 트리를 다시 대며 왜 그 레벨을 골랐는지 설명하거나,
근거가 실제로 부족했다면 재판정한다. 이건 버그가 아니라 설계다 — 판정은 반증 가능해야 한다.

**게이트 명령을 못 찾았을 때(Phase 1 이 exit 3)** — 검증 명령을 지어내지 않는다.
"이 프로젝트에서 린트는 `X`, 테스트는 `Y` 로 돌려" 라고 알려주면 그걸로 진행한다.

**작업 중간에 멈추고 싶을 때** — 그냥 멈추라고 말한다. `_workspace/` 는 삭제되지 않고
남아 있으므로 나중에 같은 대화나 새 세션에서 이어갈 수 있다.

**Human Gate 를 건너뛰고 싶을 때** — 건너뛸 수 없다. `side_effect: irreversible` 이거나
`target_environment: production` 이면 레벨과 무관하게 승인이 필요하다. 이건 의도된
안전장치다. 정말 필요 없다고 판단되면 spec 의 `task.target_environment` 나
`profile.side_effect` 판정 자체가 잘못됐는지를 먼저 확인한다.

## 무엇을 믿고 무엇을 확인해야 하는가

- **믿어도 되는 것**: 게이트 exit code, `validate-spec.py` 의 통과/실패, 훅이 막은 쓰기 시도.
  전부 결정론적 명령의 결과이지 AI 의 판단이 아니다.
- **한 번은 사람이 확인해야 하는 것**: Phase 3 의 레벨 판정 근거(반증 가능하게 쓰였는가),
  Linear 의 `blockedBy`·진행률 표시(API 가 이 값을 노출하지 않아 자동 검증이 안 된다 —
  `evals/results/linear-dry-run-2026-08-29.md` 참고), Human Gate 의 롤백 절차가 실제로
  실행 가능한 명령인가.
- **아직 실전에서 검증되지 않은 것**: H2 경로 전체, Phase 4 의 실제 에이전트 dispatch.
  `CHECKLIST.md` B-3 에 전체 목록과 확인 방법이 있다. 처음 H2/H3 를 실전에 쓸 때는
  평소보다 결과를 더 꼼꼼히 본다.
